# 案例格式与状态规则

生成或审核案例时读取本文件。字段名、顺序、数量以及正文 12 章名称不可更改。

## YAML 元数据

文件必须以 UTF-8 编码，顶部包含以下 11 个字段：

```yaml
---
知识类型: 销售微案例
案例编号: CASE-待分配
案例标题: 待确认
案例状态: 待补充
一级分类: 待分类
二级分类: 待分类
适用场景: []
来源文件: 待确认
来源载体: 待确认
信息完整度: 待补充
是否可作为已验证成功案例: 否
---
```

规则：

- `案例编号` 必须在当前知识库唯一，不复用教学样例编号。
- `案例状态` 使用“待补充 / 待审核 / 已审核（结果未核实） / 已验证成功 / 已验证未成功”等证据匹配的状态。
- `适用场景` 必须是 YAML 列表。
- `来源文件` 只列实际读取的文件；`来源载体` 写邮件、微信、WhatsApp、会议纪要或口述，不把扩展名当载体。
- `信息完整度` 使用“完整 / 部分完整 / 待补充”。
- `是否可作为已验证成功案例` 只能为“是”或“否”，并与成功状态一致。

## 固定正文

```markdown
# 销售微案例｜{案例标题}

## 一、案例一句话概括

## 二、客户与订单背景

## 三、客户提出的问题

## 四、业务员当时的想法与难点

## 五、客户真实意图分析（推断，非事实）

## 六、处理思路

## 七、参考沟通话术（知识库整理示范，非真实已发送邮件）

## 八、实际执行与客户反馈

## 九、可复用经验

## 十、适用边界与风险提醒

## 十一、后续补全字段

## 十二、知识库检索问答
```

每章都必须保留。未知事实写“未提供”或“待核实”，不要为了完整而编造。第七章的示范话术不得冒充真实发送内容；真实邮件摘录应放在第八章并注明来源。第十一章用复选框列缺口；若无缺项，写“已核对，无待补充项”。

## 文件与审计

文件名必须统一为 `CASE_知识主题_对象名称_YYYYMMDD.md`，例如 `CASE_订单取消挽回_客户追加订单_20261029.md`。`CASE` 是固定前缀；知识主题概括核心问题；对象名称使用脱敏的情境、处理结果或业务对象描述，禁止真实客户名称、简称、编码及其他可识别身份信息；日期为首次建档日期，取创建文件当天的本地日期，不得伪装为事件日期。日期一旦建档固定，后续更新不改名。清理 Windows 非法字符及路径分隔符，文件名字段内部不得使用下划线。审核状态、版本和案例编号仅保存在 YAML/索引，不写入文件名。同客户同事件更新原文件，不因状态变化新建文件；若不同事件碰巧同名，应先提示冲突并使用可辨识的知识主题，不得静默覆盖。草稿位于 `待审核/`，审核成品位于 `已审核/`。同名 `.sources.json` 可记录：案例编号、来源根目录、核验状态、每个来源文件名及 SHA-256；不要保存完整邮件正文。

## 脱敏要求（正式知识库）

- 文件名、案例标题、正文、检索问答和示范话术中不得出现可识别的真实客户名称、联系人、邮箱、电话、地址、订单号等；统一使用“某澳洲进口商”“客户A”等泛化代称。
- 来源文件字段只记录脱敏来源标识或可控内部引用编号，不直接写包含客户身份的原始文件名或绝对路径；原始证据映射仅在受权限保护的内部索引中保留。
- 订单金额、数量、具体时间等如可反向识别客户，应进行必要泛化；不能因为脱敏而编造业务事实。
- 生成前检查文件名及正文的身份信息，无法安全脱敏则暂停归档并请用户确认。
