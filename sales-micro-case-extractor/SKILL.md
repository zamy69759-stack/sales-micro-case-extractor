# 销售微案例萃取

将已授权的本地沟通资料整理为证据可追溯的销售微案例。语义判断和补问由 Codex 完成；随附脚本只负责确定性的扫描、查重、初始化和格式校验。

## 工作方式

1. 确认原始资料和输出知识库位置。路径未配置时，先完成不依赖真实路径的工作，再请用户提供路径；不要声称已读取不可访问的位置。
2. 只读扫描用户指定的文件、文件夹或时间范围。优先用 `scripts/source_reader.py` 处理 TXT、MD、EML、CSV；忽略 `._` 文件。DOCX、XLSX、PDF 若缺解析能力，明确指出并建议导出，不得假装读取。
3. 列出实际读取成功、失败、损坏和内容重复的文件。按客户、订单、时间线和主题聚合单一事件；引用的旧邮件不重复计数。若出现多个独立事件，先给出简短候选标题让用户选择，不直接批量生成。
4. 区分事实、业务员口述、推断、建议和示范话术。每项事实保留文件名、日期、主题或行号定位；不得捏造金额、日期、动作、客户反馈、交付、收款或利润。
5. 核验五项完整度：事件背景、客户问题、业务员实际动作、客户反馈、最终结果。缺关键事实时，每轮最多补问 3 个具体问题，并允许“记不清”“跳过”“先生成待补充版”。口述标为“业务员补充，待凭证核验”。
6. 生成前展示已证实事实、缺失项、拟定标题和建议状态。用 `scripts/find_duplicates.py` 检查同客户、订单、时间和相似标题；候选重复只提示更新或新建，绝不自动删除或覆盖。
7. 用户确认后，严格依照 [案例格式与状态规则](references/case-format.md) 生成一个 Markdown 文件。文件名必须遵循企业统一脱敏规则 `CASE_知识主题_对象名称_YYYYMMDD.md`，例如 `CASE_订单取消挽回_客户追加订单_20261029.md`；对象名称为脱敏业务情境或结果，不得使用真实客户名称、简称、客户编码、联系人等识别信息；日期取首次建档日期，更新不变。不可使用旧式“编号_标题_状态”命名。模板位于 `assets/micro_case.md`。草稿写入 `待审核/`，审核后才进入 `已审核/`。
8. 对成品运行 `scripts/validate_case.py`。校验失败就修复并复测。可保存同名 `.sources.json`，只记录来源定位、哈希和核验状态，不复制邮件全文。
9. 更新 `索引.csv` 时使用唯一案例编号，保留编号、标题、客户代称、事件日期、状态、订单号和相对文件路径。默认不覆盖已有案例。

## 状态边界

- 只有客户问题：生成“待补充”，不能写成成功案例。
- 有业务员动作但无客户最终反馈：写“结果待核实”。
- 客户确认继续订单但无交付或收款凭证：只能写到客户已确认的结果，不能推断已交付或已收款。
- 只有在成功结果有可核验证据且业务员审核通过后，才可同时设置“案例状态: 已验证成功”和“是否可作为已验证成功案例: 是”。

## 安全约束

不修改或删除原始资料，不自动发送消息，不上传第三方，不绕过共享盘权限，不在日志或知识卡中复制完整敏感邮件、邮箱或电话。写文件时优先使用临时文件加原子替换；覆盖已存在草稿前保留备份并征得用户同意。

## 随附脚本

- `python3 scripts/source_reader.py <文件或目录> [--output 扫描结果.json]`
- `python3 scripts/init_library.py --config <config.json>`
- `python3 scripts/find_duplicates.py <索引.csv> --title <标题> [--customer ... --date ... --order ...]`
- `python3 scripts/validate_case.py <案例.md>`

这些脚本使用 Python 标准库。脚本输出是取证和校验辅助信息，不替代人工语义判断。
